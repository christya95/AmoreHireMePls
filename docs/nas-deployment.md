# NAS deployment (Portainer, existing MongoDB)

The app runs on a NAS as the Portainer stack **`amorehiremepls`** (web + worker from one private image), deployed
from a Mac with one command and no SSH. Nothing here changes other NAS stacks, rotates credentials, exposes ports
publicly, or mounts the Docker socket into the app.

The concrete values below (UGREEN DXP4800 Plus at `192.168.2.49`, Docker Hub account `lepia`, vault `AmoreHireMePls`,
data under `/volume1/docker/amorehiremepls`, `America/Toronto`, the `christya95/job-application-records` tracker) are the
original operator's and are the defaults of `scripts/deploy_nas.sh` and `deploy/nas/compose.yaml`. To deploy your own:

| Your value | Where to set it |
|---|---|
| 1Password vault name | `OP_VAULT=<vault>` in the shell that runs the script, and in `.env.references` |
| Portainer address and endpoint | `PORTAINER_URL`, `PORTAINER_ENDPOINT_ID` |
| Docker Hub repository | `IMAGE_REPO=docker.io/<you>/amorehiremepls` (the script derives `HUB_USER`; override if different); the stack gets `AMORE_IMAGE` |
| NAS address the dashboard listens on | `AMORE_PUBLISH_HOST` (first deploy) or `--set AMORE_PUBLISH_HOST=…`; `HEALTH_URL` follows it |
| Bind mount root on the NAS | `AMORE_DATA_ROOT` (first deploy) or `--set AMORE_DATA_ROOT=/your/path`; create it and point the `init` chown at it by redeploying |
| Timezone | `--set AMORE_TIMEZONE=Europe/London` (also sets `TZ` in the containers) |
| Checking the watched job boards by itself | `--set AMORE_DISCOVERY_SCHEDULE=08:00,16:30`: comma separated 24 hour `HH:MM` times of day in `AMORE_TIMEZONE`. Empty (the default, in the code and in the compose file) means the boards are read only when someone presses "Check for new jobs". See section 4a. |
| Tracker | `--set AMORE_TRACKER_ENABLED=false`, or `true` plus `--set AMORE_TRACKER_REMOTE_URL=https://github.com/<you>/<records>.git` |
| Sign in with saved logins | `--set AMORE_SITE_SIGNIN=false` turns it off for the stack (default `true` here; the Settings switch overrides either). The containers need nothing else: no 1Password tool, no token. The owner presses Allow 1Password on a dashboard that runs where 1Password and `op` are installed, and it must share this database and `AMORE_APP_SECRET`. |
| Database network and name | the compose file joins the existing `mongodb_default` network and database `amorehiremepls`; change those two lines if yours differ |

## 3. Stack design (`deploy/nas/compose.yaml`)

- Image `docker.io/lepia/amorehiremepls:${AMORE_IMAGE_TAG}`; the tag is the 12-character git sha of the commit built; `:latest`
  is pushed too. Portainer stack environment variables carry the tag and the five secrets (names only in the file):
  `AMORE_APP_PASSWORD`, `AMORE_APP_SECRET`, `AMORE_MONGODB_USERNAME`, `AMORE_MONGODB_PASSWORD`, `OPENAI_API_KEY`, plus optional
  `AMORE_PUBLISH_HOST`, `AMORE_MODEL`, `AMORE_BROWSER_ALLOWED_HOSTS`, `AMORE_CANDIDATE_DIR` (default `/candidate`),
  `AMORE_DISCOVERY_SCHEDULE` (default empty, section 4a).
- **Candidate folder.** `/volume1/docker/amorehiremepls/candidate` is mounted at `/candidate` (writable on `web`, read-only on
  `worker`); `init` creates it and gives it to uid 10001 like the other data directories. Because the NAS has no SSH, the
  Profile page has an upload form ("Add a resume or career notes": `.docx`, `.md`, `.txt`, 5 MB cap, sanitized basename) that
  writes into this folder; the worker reads it on every fit check and tailoring. Adopting the uploaded DOCX as the base resume
  remains a separate button on the same card.
- Database: the stack's default network **is** `mongodb_default` (external), so the app reaches the database as
  `mongodb://mongodb:27017/?directConnection=true` without crossing the host interface. The `mongodb` stack is untouched.
- **Path layout.** Records written by the Mac instance store paths relative to the repository root (`runtime/artifacts/...`,
  `runtime/private/...`) and every consumer (`Path(doc["path"])`, the download route's `resolve()` + `is_relative_to(artifact_dir)`)
  resolves them against the process working directory. The containers therefore mount the data at
  `/runtime/{artifacts,private,logs}`, set `AMORE_*_DIR` to those paths and run with `working_dir: /`. The same database rows work
  on both hosts and no path rewrite was needed. Paths recorded by the NAS instance are absolute (`/runtime/...`); the Mac
  instance cannot serve those, which is one more reason to run only one instance (section 6).
- Hardening kept from the repository compose: non-root uid 10001, `cap_drop: ALL`, `no-new-privileges`, 1.5 CPU / 1536 MB,
  json-file log rotation, `shm_size: 512m` for Chromium, health checks (`/health`, `amore worker-health`), `restart: unless-stopped`,
  no Docker socket. The image's unused `VOLUME /data` is backed by a 1 MB tmpfs so no anonymous volumes accumulate.
- **Seccomp.** The repository compose references `deploy/seccomp_profile.json` (Playwright's profile, which keeps Chromium's own
  sandbox usable). Portainer's compose client runs inside the Portainer container and can only read files that are part of the
  stack, so the NAS stack keeps Docker's default seccomp profile. Playwright launches Chromium with the Chromium sandbox disabled
  by default (`chromium_sandbox=False`), which is the standard container setup; verified on the NAS worker container
  (`chromium 156.0.8078.4` launched headless and rendered a page; LibreOffice 24.2.7 present). The `init` service runs as root for
  the `chown` only and has `network_mode: none`.
- **Publishing.** The dashboard is published on `${AMORE_PUBLISH_HOST:-192.168.2.49}:8790`. Binding the LAN address does not answer
  on the Tailscale address (no subnet route, and a socket bound to one address ignores the other); binding the Tailscale address
  directly is not done because `tailscale0` belongs to the `nas-tailscale` container and may not exist yet when Docker starts the
  stack at boot (a failed port bind is not retried by the restart policy). To reach the dashboard remotely over the tailnet, set the
  stack variable `AMORE_PUBLISH_HOST=0.0.0.0` (all NAS interfaces, like the other stacks on this NAS; the dashboard still requires
  the password and CSRF tokens) or use a Tailscale Serve rule on the NAS. The current choice is the LAN address.

## 4. Deploying and redeploying (one command)

```bash
scripts/deploy_nas.sh                  # build HEAD for linux/amd64, push :sha and :latest, create/update stack 7, wait healthy, GET /health
scripts/deploy_nas.sh --skip-build     # re-apply the compose file / env for the tag already pushed for HEAD
scripts/deploy_nas.sh --tag <sha>      # roll back or forward to an already pushed tag
scripts/deploy_nas.sh --skip-build --tag <sha> --set AMORE_BROWSER_ALLOWED_HOSTS=host1,host2   # change a non-secret stack variable
scripts/deploy_nas.sh --skip-build --set AMORE_PUBLISH_HOST=0.0.0.0                              # change the publish address
```

Non-secret stack variables not managed by the script (everything except `AMORE_IMAGE`, `AMORE_IMAGE_TAG` and the five vault secrets) are
carried over from the stack's current environment, so a `--set` value sticks until changed; secret names cannot be `--set`.
The script prints the env names it applied (never values). `--skip-build` refuses a HEAD whose tag was never pushed; pass
`--tag` with the running tag for config-only changes (`AMORE_IMAGE_TAG` in Portainer shows it).

The script builds from a clean `git archive HEAD` export (uncommitted edits are never shipped; it prints a note when the tree is
dirty), reads every secret through `op` at run time (`docker login --password-stdin`; `op run` → Python builds the JSON body in
memory), creates the stack with `POST /api/stacks/create/standalone/string` or updates it with `PUT /api/stacks/{id}`
(`pullImage: true, prune: true`), then waits until `web` and `worker` are recreated after the request and healthy, and finally checks
`http://192.168.2.49:8790/health`. It is idempotent; running it twice with the same HEAD is a no-op redeploy.

### 4a. Checking the job boards on a schedule (`AMORE_DISCOVERY_SCHEDULE`)

The worker reads the setting; the compose file passes the same stack variable to `web` and `worker`. The value is a list of times of
day, not a cron line: `08:00,16:30` means every day at 08:00 and at 16:30 in `AMORE_TIMEZONE`. The original operator's stack is set
to exactly that (twice a day, morning and late afternoon, `America/Toronto`), applied on 2026-11-13 with

```bash
scripts/deploy_nas.sh --set AMORE_DISCOVERY_SCHEDULE=08:00,16:30     # sticks across later deploys like every other --set value
scripts/deploy_nas.sh --skip-build --tag <running sha> --set AMORE_DISCOVERY_SCHEDULE=      # turn it off again
```

The script refuses an entry that is not `HH:MM`. What a time of day does when it comes due:

- It queues one check, the same kind "Check for new jobs" queues, and the same single pass reads the boards. A button pressed around
  the same minute and the scheduled check are one read, not two. If a check is already waiting or running, nothing is queued.
- Each time of day on each date is claimed once in the database (`scheduler_slots`), so a restart, a redeploy or a second worker
  never repeats it. A worker that was off when the time passed makes up for it within 6 hours, and only for the latest time it
  missed: being off through several times of day costs one check, not one for each.
- A posting the app already knows is not sent to the model again, so a check that finds nothing new costs no model call. A posting
  whose text did not change keeps its place in All jobs; a new or changed one moves to the top.
- At its first pass the worker logs `discovery schedule: 08:00, 16:30 (America/Toronto)` and saves the same in the database
  (`controls.discovery_schedule`). The Jobs page reads that record, so a dashboard on another computer (the Mac one, whose own `.env`
  has no schedule) still says "Next automatic check today at 16:30. The last one ran today at 08:00." With no time set the page says
  nothing about it and Overview says "disabled".

## 6. One instance: the NAS (since 2026-11-05 03:20)

The Mac `amore web` / `amore worker` processes were stopped (SIGTERM to the `op run` wrappers; PID files removed) after image
`a590080de7c3` was deployed and the Faire documents had been regenerated on the NAS with the preserved header block. The NAS stack is
the only runtime. Running a second instance against the same database is safe (runs, actions and sync items are claimed atomically,
an `executing` action is never taken over, expired leases become `needs_verification`) but doubles scheduled discovery/model spend,
and artifacts tailored on one host are not on the other's disk (the download route then answers 404 "file missing on this host" or
403 for a path outside its artifact directory). If the Mac instance is ever started again for debugging, stop it afterwards.
The worker heartbeat (`controls.worker_heartbeat`, name = container hostname) shows which host is alive.

## 10. Running the test suite against the NAS

The fixtures accept a fixed throwaway database so a `readWrite`-only user works (collections are dropped between tests instead of
the database):

```bash
printf 'U=op://AmoreHireMePls/NAS MongoDB App User/username\nP=op://AmoreHireMePls/NAS MongoDB App User/password\n' > /tmp/app.env
op run --env-file /tmp/app.env -- sh -c 'AMORE_TEST_MONGODB_URI="mongodb://$U:$P@100.90.96.81:27017/amorehiremepls_test?authSource=amorehiremepls&directConnection=true" AMORE_TEST_MONGODB_DATABASE=amorehiremepls_test uv run pytest -m mongo -q'
rm /tmp/app.env
```

The app user needs `readWrite` on `amorehiremepls_test` and `amorehiremepls_test_restored` (backup test) for the duration; grant
with the root session, revoke afterwards. 2026-11-04 result: 55 passed in about 10 minutes.
