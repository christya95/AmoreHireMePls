# NAS deployment (UGREEN DXP4800 Plus, Portainer, existing MongoDB)

The app runs on the NAS as the Portainer stack **`amorehiremepls`** (web + worker from one private image), deployed
from the Mac with one command and no SSH. Nothing here changes other NAS stacks, rotates credentials, exposes ports
publicly, or mounts the Docker socket into the app.

Why Docker Hub and not GHCR: the `gh` login on the Mac has scopes `repo, read:org, gist, admin:public_key` only (no `write:packages`
/ `read:packages`), and a new GitHub PAT cannot be minted headlessly. The Hub login in the Personal vault has no 2FA, so scoped
tokens could be created through the Hub API without touching the password again. Switching to GHCR later only needs
`IMAGE_REPO`, a registry entry and the two tokens.

## 3. Stack design (`deploy/nas/compose.yaml`)

- Image `docker.io/lepia/amorehiremepls:${AMORE_IMAGE_TAG}`; the tag is the 12-character git sha of the commit built; `:latest`
  is pushed too. Portainer stack environment variables carry the tag and the five secrets (names only in the file):
  `AMORE_APP_PASSWORD`, `AMORE_APP_SECRET`, `AMORE_MONGODB_USERNAME`, `AMORE_MONGODB_PASSWORD`, `OPENAI_API_KEY`, plus optional
  `AMORE_PUBLISH_HOST`, `AMORE_MODEL`, `AMORE_BROWSER_ALLOWED_HOSTS`.
- Database: the stack's default network **is** `mongodb_default` (external), so the app reaches the database as
  `mongodb://mongodb:27017/?directConnection=true` without crossing the host interface. The `mongodb` stack is untouched.
- **Path layout.** Records written by the Mac instance store paths relative to the repository root (`runtime/artifacts/...`,
  `runtime/private/...`) and every consumer (`Path(doc["path"])`, the download route's `resolve()` + `is_relative_to(artifact_dir)`)
  resolves them against the process working directory. The containers therefore mount the data at
  `/runtime/{artifacts,private,logs}`, set `AMORE_*_DIR` to those paths and run with `working_dir: /`. The same database rows work
  on both hosts and no path rewrite was needed. Paths recorded by the NAS instance are absolute (`/runtime/...`); the Mac
  instance cannot serve those, which is one more reason to run only one instance (section 6).
- Hardening kept from the repository compose: non-root uid 10001, `cap_drop: ALL`, `no-new-privileges`, 1.5 CPU / 1536 MB,
  json-file log rotation, `shm_size: 512m` for Chromium, health checks (`/health`, `amore worker-health`), `restart: unless-stopped`,
  no Docker socket. The image's unused `VOLUME /data` is backed by a 1 MB tmpfs so no anonymous volumes accumulate.
- **Seccomp.** The repository compose references `deploy/seccomp_profile.json` (Playwright's profile, which keeps Chromium's own
  sandbox usable). Portainer's compose client runs inside the Portainer container and can only read files that are part of the
  stack, so the NAS stack keeps Docker's default seccomp profile. Playwright launches Chromium with the Chromium sandbox disabled
  by default (`chromium_sandbox=False`), which is the standard container setup; verified on the NAS worker container
  (`chromium 156.0.8078.4` launched headless and rendered a page; LibreOffice 24.2.7 present). The `init` service runs as root for
  the `chown` only and has `network_mode: none`.
- **Publishing.** The dashboard is published on `${AMORE_PUBLISH_HOST:-192.168.2.49}:8790`. Binding the LAN address does not answer
  on the Tailscale address (no subnet route, and a socket bound to one address ignores the other); binding the Tailscale address
  directly is not done because `tailscale0` belongs to the `nas-tailscale` container and may not exist yet when Docker starts the
  stack at boot (a failed port bind is not retried by the restart policy). To reach the dashboard remotely over the tailnet, set the
  stack variable `AMORE_PUBLISH_HOST=0.0.0.0` (all NAS interfaces, like the other stacks on this NAS; the dashboard still requires
  the password and CSRF tokens) or use a Tailscale Serve rule on the NAS. The current choice is the LAN address.

## 4. Deploying and redeploying (one command)

```bash
scripts/deploy_nas.sh                  # build HEAD for linux/amd64, push :sha and :latest, create/update stack 7, wait healthy, GET /health
scripts/deploy_nas.sh --skip-build     # re-apply the compose file / env for the tag already pushed for HEAD
scripts/deploy_nas.sh --tag <sha>      # roll back or forward to an already pushed tag
AMORE_PUBLISH_HOST=0.0.0.0 scripts/deploy_nas.sh --skip-build   # change the publish address
```

The script builds from a clean `git archive HEAD` export (uncommitted edits are never shipped; it prints a note when the tree is
dirty), reads every secret through `op` at run time (`docker login --password-stdin`; `op run` → Python builds the JSON body in
memory), creates the stack with `POST /api/stacks/create/standalone/string` or updates it with `PUT /api/stacks/{id}`
(`pullImage: true, prune: true`), then waits until `web` and `worker` are recreated after the request and healthy, and finally checks
`http://192.168.2.49:8790/health`. It is idempotent; running it twice with the same HEAD is a no-op redeploy.

First deploy on 2026-11-05: stack 7 created in about 90 s (image pull included), `init` exited 0, web and worker healthy,
`/health` 200, the sign-in page renders, `/status` (authenticated) reports Mongo 8.0.34 and the worker heartbeat.

## 6. Two instances, one database

The Mac instance (`amore web` / `amore worker` through `op run`, see README) was left running. Two workers against one database
are safe: runs, actions and sync items are claimed atomically, an `executing` action is never taken over, and expired leases become
`needs_verification`. Normal operation is still **one** worker: two workers double the scheduled discovery/model spend, and
artifacts tailored on one host are not on the other's disk (the download route then answers 404 "file missing on this host" or 403
for a path outside its artifact directory). Recommended once the NAS stack has been healthy for a day: stop the Mac worker
(`kill $(cat runtime/logs/worker.pid)` or the README stop command), keep or stop the Mac web, and treat the NAS as the only
runtime. Joss decides when.

| `Docker Hub Pull Token` | Portainer registry id 1 | `repo:read`. |
| `Dashboard Password`, `App Session Secret`, `NAS MongoDB App User`, `OpenAI API Key` | Portainer stack env (set at each deploy from the vault) | Portainer stores stack env values in its database on the NAS (`/volume1/docker/portainer/data`); treat that volume as sensitive, as it already is for the mongodb stack's root credentials. |

Rotating any of these: update the vault item, run `scripts/deploy_nas.sh --skip-build` (stack env) or recreate the registry entry
(pull token). Nothing is written to `.env` files on the NAS.

## 10. Running the test suite against the NAS

The fixtures accept a fixed throwaway database so a `readWrite`-only user works (collections are dropped between tests instead of
the database):

```bash
printf 'U=op://AmoreHireMePls/NAS MongoDB App User/username\nP=op://AmoreHireMePls/NAS MongoDB App User/password\n' > /tmp/app.env
op run --env-file /tmp/app.env -- sh -c 'AMORE_TEST_MONGODB_URI="mongodb://$U:$P@100.90.96.81:27017/amorehiremepls_test?authSource=amorehiremepls&directConnection=true" AMORE_TEST_MONGODB_DATABASE=amorehiremepls_test uv run pytest -m mongo -q'
rm /tmp/app.env
```

The app user needs `readWrite` on `amorehiremepls_test` and `amorehiremepls_test_restored` (backup test) for the duration; grant
with the root session, revoke afterwards. 2026-11-04 result: 55 passed in about 10 minutes.
